# Stage 2 — isolated notification backend candidate (NO DEPLOY)

## Scope
Built on the stage-1 core, without changing any existing production file or entry point. No real credentials, personal records, master ID, real messages, live write, OAuth callback, trigger, or API route. Do not install this candidate into the running Apps Script until all release gates below are met.

- `study-notification-service.js`: settings compare-and-swap; trusted adapter contracts; exclusive execution; per-slot reservation; same-day/round exclusion; per-topic and immutable per-part reservations; request marker before transport; confirmed/rejected/unknown handling; held unknown results after crash; partial continuation within the current assigned day and send window; configurable caps; isolated status.
- `study-notification-gas-store.gs`: dedicated single-writer append-only Sheets journal, ScriptLock, complete batch/checksum validation and write readback. Explicit constructor only, exact workbook/tab/header check, no auto initialization. Requires separate private workbook; never points at MASTER.
- `study-notification-plan-reader.js`: exact existing plan and schedule headers, explicit plan ID, ACTIVE three-round metadata, selected active revision, per-chunk SHA-256 and canonical snapshot SHA-256, counts/date continuity, revision recheck, read-only topic mapping to eight fields. The reader itself is NOT an authorization boundary. Its GAS adapter must only be invoked by a trusted single-owner server.
- `study-notification-stage2.test.cjs`: synthetic fixtures; tests CAS, per-slot and per-part durability, unknown crash recovery, time boundaries, source integrity, and simulated GAS journal. No real network or user records.

## Next steps / blockers
1. On the actual device containing the target plan, verify the plan name/ID, export existing plan and progress backups using existing UI, inspect first-migration/sync status, then use existing approved authenticated migration workflow. Never overwrite another device's data or modify MASTER study text. Do not send without a committed verified plan.
2. Implement actual independent authorized server routing/identity, OAuth state/CSRF, single-account ownership binding, secure token store and refresh, explicit disconnect, official Kakao self-message transport, free quota guard, and scheduler. Fail closed until account and plan are both verified; no user input may forge the trusted reader/gate. Exact plan name must be selected by owner and bound to plan ID. Do not enable timers during development.
3. The journal is a correctness prototype, NOT a production-scale storage solution. Full replay is O(history), bounded at 150000 rows; long three-round schedules with many parts may hit cell/row/time limits. Implement indexed durable storage or verified compaction/partitioning, retain date and round dedupe and immutable parts, benchmark realistic data under GAS runtime/quota limits. Check pending job membership and current source active/excluded/deleted status before further sends (reserved original parts remain unchanged). Confirm behavior for known rejected parts and explicit user resolution of unknown delivery; no blind retries. Bound request rate and daily/app quota separately from per-slot caps. A call started before 20:00 may be accepted after 20:00; enforce no new call after cutoff and report distinction.
4. Review deployed planner host and signed API, integrate authenticated settings CAS, preview/test (explicit separate action), progress/history/unsent display, and existing PWA UI. Distinguish sent from learned. Show local-only plans as unavailable for cloud sends. Verify latest plan identity and existing ACTIVE/HMAC/nonce auth; no unauthenticated settings endpoint.
5. Run real staging GAS/Sheets/browser checks, test successful Kakao self-message only with owner participation and explicit approved test. Verify Kakao policy and token lifetime/quotas. No actual push notification via self-message. Separate user approval required for main merge, production GAS deployment and automatic trigger activation.

## Proposed defaults, not provider guarantees
Five-minute slots, max five topics/20 part attempts per slot, 08:30 inclusive to 20:00 exclusive Asia/Seoul, disabled until configured. All original selected text preserved in parts; if remaining slots cannot finish, retain unsent state and show capacity warning. No automatic next-day rollover. Any uncertain outcome must be held, not claimed as confirmed.
