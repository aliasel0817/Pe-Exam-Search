## 3. Apps Script pdfPageFiles 응답 모양으로 재조회 테스트
- 서버 설계 응답: 6개 파일 컬럼(출처유형, 페이지키, 페이지번호, 페이지토큰, 페이지Drive파일ID, 페이지파일명) + 8개 관계 컬럼(자료유형, 기준페이지키, 기준페이지토큰, 삽입위치, 대체대상페이지토큰, 논리순서, 판본, 활성여부).
- 실제 HTML의 `normalizeReferencePdfPages`와 `buildReferencePdfLogicalSequence` 및 순차 이동 함수를 Node VM 테스트 환경에서 그대로 로드해 검증.
- 독립 신규 서브노트 원본 `MG-6:1→MG-6:2`는 구 MG:1~3과 **재조회 후에도 분리**되어 앞으로/뒤로 이동.
- 기존 원본 SW-2:613에 개정 `-R3` 3페이지 + 보강 `-ADD1` 2페이지를 결합할 때 **R3:613→R3:614→R3:615→ADD1:1→ADD1:2→원본 614...** 순서 확인.
- 구 개정 `-R2` 본문과 연속 페이지는 최신 `-R3` 흐름에서 제외.
- 서버에 중복 페이지토큰 또는 필수 Drive 파일ID 공란이 있으면 기존 정규화 함수가 오류를 발생시키는지 확인.

## 4. 개정 3페이지 중간 실패/재시도 모의시험
- 기준 원본 `SW-2:613`, 신규 개정 `SW-2-R4:613,614,615` 가상 사례.
- 업로드 순서 **`:614`(폴더 생성) → `:615` → `:613`(개정 첫 장 최종 발행)** 유지.
- `:614` 업로드 성공, `:615` 네트워크 실패를 시뮬레이션. 실패 직후 화면의 기존 SW-2:613 원본은 그대로 남고, 미완성 -R4 연속 페이지는 보이지 않음.
- 같은 관리창에서 재시도 시 **`:615` → `:613`** 두 장만 추가 업로드. 이미 성공한 `:614` 중복 업로드 없음, 기존 원본 Drive 파일ID 유지.
- 이 시험은 실제 Google Drive/Apps Script에 파일을 생성하거나 네트워크를 강제로 끊은 시험이 아님. **모의 검증**임.

## 5. 서버 메타데이터 설계 주의사항
- 다중 페이지 개정의 첫 업로드는 **보강 관계**를 가진 계속 페이지임. 따라서 서버가 신규 -R 키를 처음 생성할 때 페이지키 등록표의 자료유형이 **보강**으로 기록될 가능성이 있음. 다만 개별 페이지 관계는 계속 페이지 보강·첫 페이지 개정으로 구분되어 뷰어가 최신 개정 문서를 재구성함.
- 아직 운영 `PDF페이지관계_20260930`에는 검증 가능한 보강·개정 관계 레코드가 없으므로 실제 -R 등록으로 **페이지키 메타데이터와 관계행의 정합성 시험이 필요**함. 오류로 확정하거나 기존 데이터를 수정하지 않음.

## 6. 앞으로 할 실제 QA
1. 새 서브노트 원본 **2페이지** 실제 업로드 (기존 자료에 없는 신규 페이지키/안전 시험 토픽), 첫 장 연결/원본 다음·이전/새로고침 재조회.
2. 기존 원본 누락 번호 보충 (중복없는 시험범위만).
3. 보강 `-ADD` 2~3페이지 앞·뒤 삽입 시 관계행·순차보기 확인.
4. 개정 `-R` 2~3페이지 발행 시 **신규 페이지키 등록표의 자료유형, 개별 관계행, 원본 보존, 새로고침 이동** 확인.
5. 직접 다중 교체 → 새 개정 코드 발급 및 원본 Drive ID 보호 확인.
6. Galaxy Tab/iPhone 터치·확대·관리 팝업·PDF 이동 QA; 중간 네트워크 오류는 테스트 계정/자료에서만.
7. 검증 중 오류가 나오면 코드를 별도 수정·검사 후 반영하고, 사용자 통합 매뉴얼에 증상/조치를 덧붙임.
