## 0. 최우선 작업 지시

M0~M6에서 이미 구현·검증한 MuPDF.js 렌더러를 **새로 개발하지 말고 재사용**하고, 남은 결함을 직접 수정하여 서브노트·교재·첨부 PDF 뷰어를 통합 안정화한다.

대상 원격 PC, 절대 작업 경로, Git 저장소, 최신 main, 모든 열린 PR과 타 채팅 작업 영역을 먼저 확인한다. 원본·미커밋·공유 프로세스를 보호하고 독립 브랜치와 독립 폴더에서 작업한다.

- M7에서 실제 구현을 마친 후 필수 자동검사와 실제 Chrome 검사를 실시한다.
- 접근이 허가된 PC·태블릿·iPhone의 **물리적 실기기** 검사 결과를 Chrome 모바일 에뮬레이션과 엄격히 구분한다.
- 실제 기기/인증정보/법률 확인이 안 된 사항은 통과로 처리하지 않으며 공개 배포 불가 조건으로 명시한다.
- AGPL 관련 Apps Script 서버 결합, 대응 소스 범위, MuPDF WASM 재빌드 요건이 미확정 상태라 **외부 공개·GitHub Pages·공개 테스트 서버·타 사용자에게 MuPDF JS/WASM 배포 절대 금지**.
- 운영 main 병합/배포와 실제 Apps Script 설정·코드 변경은 별도의 사용자 명시적 승인 전까지 금지.

### M7-6. AGPL 대응 소스 및 공개 가능성 판단 (운영 배포 차단)

현재 미해결:

1. 브라우저 MuPDF JS/WASM과 Apps Script HTTP API 결합 관계에 따른 AGPL 대응 소스 공개 범위.
2. 프런트/서버 대응 소스 제공 파일·변경 코드·빌드/설치 스크립트의 정확한 범위.
3. MuPDF C 원본에서 배포한 WASM을 다시 빌드할 수 있는 소스·스크립트·제3자 의존성 완전성.
4. 라이선스 고지·NOTICE·제3자 라이브러리 라이선스 충돌 가능성.
5. Script Properties·비밀키·사용자 데이터와 공개 코드의 분리.
6. 필요 시 Artifex 또는 자격 있는 법률 전문가의 서면 판단 또는 적합한 상용 라이선스.

**이들 항목이 해결되지 않으면 M7 개발과 비운영 검증은 완료 가능하더라도 외부 공개/운영 배포는 절대 GO 판정하지 않는다.** M2 release gate는 계속 CLOSED. 기존 PDF.js를 사용한 운영 앱은 임의 교체하지 않는다.

### M7-7. 보안 및 권한 수용검사

- 원본 PDF signed GET, mediaContent GET의 인가·만료·기기 ACTIVE/PENDING/REVOKED 처리.
- 데이터 추가·수정·삭제는 현재 소유자만 수행하는 기존 정책을 유지. 공개 조회 허용 정책을 임의로 막지 않음.
- 구형 PDF.js CVE 완화/안전 버전 fallback가 실제 통합 경로에 빠짐없이 적용되는지 확인.
- Service Worker/브라우저 저장소에 PDF 원본·signed URL·민감 필기/토큰이 의도치 않게 캐시되지 않도록 확인.
- 실제 서버 secret/Script Properties 공개·변경 금지. 보안 테스트도 읽기 전용 또는 격리된 합성 환경 원칙.

## 5. M7 수행 순서와 개발·검증 운영

1. 최신 GitHub/원격 PC/PR 확인.
2. M7 독립 작업 경로·브랜치 생성(최신 M6 HEAD 기준).
3. 가장 영향도가 큰 통합 결함과 M7의 변경 대상 확정.
4. 해당 결함을 실제 개발 코드로 수정하고 단위검사 추가.
5. PDF 화면 3종 고화질·필기·제스처·고배율·Worker 핵심 자동검사.
6. 합성 PDF만 사용하는 로컬 실제 Windows Chrome 회귀검사.
7. 안전한 환경과 적법성이 확보되면 실제 ACTIVE 기기 read-only PDF 조회 및 실제 PC·Tab S11·iPhone Safari 검수. 불가능하면 미검증 명시.
8. AGPL·대응 소스·비밀정보·M2 공개 차단/정적 asset 무결성 점검.
9. 중대 문제 발견 시 해당 경로 수정 후 핵심 검사만 재수행. 경미 문제는 후속 이슈로 정리.
10. 독립 브랜치 commit/Push, integration 대상 Draft PR 생성, GitHub Actions 확인.
11. 최종 M7 상세 결과 보고서, 운영 병합·공개 승인 전 검사표, 가능/불가 조건과 잔여 위험 작성.
12. 이 채팅에서는 **어떤 운영 main 병합·Apps Script 변경·Pages/MuPDF 배포도 수행하지 않음**.

M7은 최종 품질 단계여서 M1~M6의 개발 60~70% 비중을 엄격한 할당량으로 강제하지 않되, 조사·중복 검토보다 발견된 결함의 실제 코드 수정에 우선순위를 부여한다. 실제 개발/검증 소요를 측정하지 못했다면 추정 비중을 실측으로 보고하지 않는다.

## 6. M7 합격/차단 기준

**개발·비운영 검증 완료 조건**

- 기존 서브노트·교재·첨부 PDF가 M7 로컬 비운영 환경에서 MuPDF로 원본 렌더되고 M3 PDF.js fallback으로 복구.
- 첫 로딩, 고화질 타일, 0/90/180/270 rotation/CropBox, 확대 1x~10x, DPR·fit, 페이지/첨부 이동, Worker abort/close의 핵심 검증 PASS.
- 기존 주석 스키마3/normalized 좌표, 페이지 키·사용자별 필기 구조 및 데이터 보존.
- 원본 signed GET·mediaContent/owner-only API의 함수·정책 보존.
- 기존 M1~M6 자동검사 및 M7 새 검사 통과. 실제 브라우저 검증과 실기기 검증 분리.
- GitHub Draft PR과 대응 소스·개발 결과·M7 보고서 확보.
- 운영 main, Apps Script, LIVE MASTER, Drive, 실제 필기·원본 PDF·GitHub Pages **변경 0**.

**운영 공개 가능 조건(별도, 사용자 명시적 승인 필요)**

- AGPL 법률 검토와 대응 소스·WASM 완전성/고지 체계가 실제 배포 방식에 대해 충족됨.
- 운영 비밀정보/사용자 데이터의 소스 공개 분리 검증.
- 요청된 실제 PC·Galaxy Tab S11·iPhone 16 Pro 검수가 완료되거나 사용자에게 공개적으로 미검증 위험을 명확하게 설명하고 별도 승인받음.
- 운영 인증·원본 PDF·실제 필기/동기화 안전성 확인.
- 사용자의 **별도 운영 main 병합/배포 승인**. M7 브랜치 또는 Draft PR 작성이 자동 배포 승인이 아님.

법률·인증·데이터 보존 위험이 해결되지 않았다면 운영 배포 결과를 완료/GO라고 표기하지 말 것.

## 9. 최종 지시

**이번 채팅에서는 M7 최종 통합 안정화·필수 검증을 개발 브랜치에서 완료할 수 있는 범위까지 직접 수행한다.**
