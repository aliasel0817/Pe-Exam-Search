# R4 — MuPDF.js AGPL 적용 판단과 준수 경로 (법률 리스크 검토, 미확정 부분 표시)

**분석일:** 2026-11-04 (Asia/Seoul)
**대상:** `mupdf@1.28.1` AGPL-3.0-or-later / 정보관리기술사 학습노트 PDF Worker·브라우저 앱 / Google Apps Script API / GitHub Pages
**범위:** 공개된 법률 문구와 라이선스 권리자 설명을 바탕으로 한 기술적 컴플라이언스 의견. 변호사의 정식 법률 자문·Artifex 승인 또는 계약이 **아니다**. 본 문서만으로 배포를 해제하지 않는다.

## 1. 확인된 법률·약관 근거

1. `mupdf@1.28.1` 공식 npm 패키지의 라이선스 표시는 `AGPL-3.0-or-later`. JS wrapper뿐 아니라 브라우저에 다운로드되는 MuPDF WASM에도 적용됨.
   - https://www.npmjs.com/package/mupdf
   - https://mupdfjs.readthedocs.io/en/latest/faq/index.html
2. Artifex 공식 라이선스 안내: AGPL 방식으로 서비스에 통합하여 사용하는 경우 애플리케이션 코드의 소스 공개를 요구한다고 명시; 그 의무를 이행할 수 없다면 상용 라이선스 필요.
   - https://artifex.com/licensing
3. GNU AGPLv3 §1: Corresponding Source는 사용·생성·설치·수정에 필요한 소스와 제어 스크립트 등이며 System Libraries 예외가 있음. §5, §6: 수정/객체 코드 배포 및 소스 제공 의무. §13: 수정된 AGPL 프로그램과 네트워크 원격 이용자 간 상호작용 시 관련 대응 소스 제공 권리.
   - https://www.gnu.org/licenses/agpl-3.0.html
   - https://opensource.org/license/agpl-3-0
4. GNU FAQ는 **최종 바이너리의 SHA-256 완전 동일성을 별도 의무로 요구하지 않는다고 명확하게 설명**한다. 필수는 배포 객체코드에 실제로 대응하고 재빌드·수정 가능한 소스와 설치·빌드 자료라는 뜻.
   - https://www.gnu.org/licenses/gpl-faq.en.html#MustSourceBuildToMatchExactHashOfBinary
   - https://www.gnu.org/licenses/gpl-faq.en.html#AGPLv3CorrespondingSource

## 2. 이 프로젝트에 대한 판단

| 질문 | 위험 및 실무 결론 |
|---|---|
| MuPDF C 원본을 수정하지 않은 경우에도 준수해야 하나? | **예**. WASM/JS를 브라우저로 제공하는 행위 자체가 배포물 전달에 해당하고, 결합 애플리케이션의 AGPL 적용/소스 제공 의무를 검토해야 한다. |
| MuPDF 라이브러리 소스만 공개하면 충분한가? | **아니라고 가정하고 준비해야 함**. Artifex는 통합된 애플리케이션의 전체 소스 공개를 요구한다고 안내. 기존 GitHub 저장소가 공개라는 사실만으로 배포 버전과 완전한 대응 소스·설치정보 제공을 증명하지 못함. |
| Apps Script는 별도 HTTPS 서버라 AGPL 적용을 면할 수 있는가? | **판단 불확실**. 별도 프로세스/HTTP API는 고려 요소지만, 통합 정도·데이터/제어 결합에 따라 독립/결합 여부가 다툼의 여지가 있음. Artifex/전문가 서면 확인 전에는 서버가 당연히 제외된다는 전제로 공개하지 않음. |
| Google Sheets LIVE MASTER, 실제 PDF·필기, HMAC/Script Properties도 공개해야 하나? | 통상 프로그램의 **개인정보·사용자 콘텐츠·비밀키는 소스 코드 그 자체가 아니다**. 제외를 전제로 설계하되, 기능 설치·재현에 필요한 코드는 비밀값이 없는 예시 설정·설치 절차로 제공. 제거 과정에서 필수 대응 소스가 결여되면 안 됨. |
| Source offer 링크만 만들면 되는가? | **아니오**. 링크는 실제 배포 버전에 맞는 충분한 소스·빌드/설치 자료를 누구나 접근 가능한 형태로 제공해야 함. 존재하지 않는 링크, 외부 공개 전에 비공개 계정이나 토큰을 요구하는 URL, placeholder는 금지. |
| 동일 해시의 재빌드가 안 되면 무조건 불법인가? | **아니오**. 빌드 결과의 바이트 동일성은 권장 품질 근거. 대응 소스가 충분한지는 별개의 판단. 그러나 현재 실제 C→WASM 빌드를 해보지 않았으므로 **완전한 대응 소스 입증도 완료되지 않음**. |
| 기존 학습노트 원본 PDF의 PDF Producer/Metadata를 바꿔야 하나? | **아니오**. Artifex의 producer line은 PDF를 생성·변경하는 경우의 권고 맥락. 원본을 단순 렌더하는 학습노트에서는 원본 PDF 메타데이터를 변경하지 않는다. |
| 상용 계약을 하면 소스 공개하지 않아도 되는가? | **계약된 사용 범위 내에서는 가능할 수 있음**. 사용자 수, 제공 플랫폼/사이트/배포 유형, SaaS/클라이언트 사용 범위가 실제 계약에 포함돼야 함. 계약 체결·비용 승인 없이 상용 권리를 얻었다고 주장하지 않음. |

- [ ] 서면 계약 체결/지급·사용자 승인
- [ ] 계약 대상의 모든 라이선스 파일·NOTICE·제3자 의무 유지
- [ ] 계약에서 허용한 범위로 운영 배포. 현재 AGPL으로 받은 공개판을 별도 사용 허락 없이 단순 재표기하지 않음.

**권고:** 공개해야 할 Apps Script 범위가 불분명하고 원본 인증·필기·소유자 관리 로직이 포함된 현재 구조에서는, 백엔드 구현을 비공개로 유지해야 한다면 **상용 라이선스 확보가 더 예측 가능한 경로**다. 소스 공개에 동의하고 충분한 대응 소스·공지·권리관계를 검증할 수 있다면 AGPL 준수 경로도 검토 가능하다.

## 4. 고지·표시 요건 (준비된 코드)

- `licenses/AGPL-3.0.txt`: 공식 mupdf npm 1.28.1 LICENSE 완전 복사본, M2 hash/size 대조.
- `R4-THIRD-PARTY-NOTICES-DRAFT.md`: 현 단계 라이선스와 추가 확인이 필요한 제3자 구성 기록.
- `r4-license-notice.js`: loopback `m4-local=1`에서만 동작하는 “오픈소스 고지” 접근 UI. © Artifex, 버전/라이선스, 무보증, 라이선스 전문 링크 표시.
- **현재 대응 소스 URL은 표시하지 않음**. 사용 가능한 실제 source offer가 확보되기 전에는 AGPL 준수 UI라고 주장할 수 없음.
- 운영용 최종 고지로 승격하려면 법률/권리/소스 공개 범위·사용자 승인 및 운영 HTML/UI 접근성 검수가 필요함.
