## 2. 개발 내용
- 프런트 후보 버전 `4.6.14-pdf-relation-readback`.
- 새 함수 `collectPendingReferencePdfRelationEntries`: **토픽에 실제 연결되는** 보강/개정 분할 배치만 선별. 별도 교재·서브노트, 직접 원본 행 다중 교체의 새 -R 버전도 처리.
- 새 함수 `referencePdfMaterialRelationErrors`: 서버 페이지 토큰·Drive 파일ID·관계 자료유형·기준 페이지키·보강 삽입 앵커/위치·개정 대체대상·활성여부를 각각 검증. 서버의 논리순서 번호는 업로드 시 재계산될 수 있어 동일성 비교 대상으로 삼지 않음.
- 새 함수 `verifyPendingReferencePdfMaterialRelations`: **실제 Apps Script PDF 페이지 목록을 새로 요청**해 검증하며, 이전 캐시나 단일 업로드 성공 응답을 신뢰해 관계검사를 생략하지 않음.
- `saveManagedTopic` 순서:
  1. 신규 PDF 페이지별 업로드
  2. **보강·개정 분할 PDF의 서버 관계 재조회/검증**
  3. 페이지 연결 검증
  4. 기존 PDF 교체의 안전한 후속 확인
  5. **토픽 내용 저장 및 링크 갱신**
- 검증에 실패하면 토픽 변경을 중단하고 관리창을 유지. 성공한 신규 Drive 파일을 삭제하지 않으므로 서버 상태를 확인하고 동일 창에서 안전 재시도.
- 실패한 재조회 때문에 업로드 성공이 실패로 오해되는 것을 피하도록 오류 문구에서 '이미 업로드됐을 수 있음' 안내.
- 새 원본/누락 원본/1페이지 기존 경로는 변경 없음.

## 3. 자동 테스트 항목
- 교재 개정 3페이지(`-R`)와 서브노트 보강 2페이지(`-ADD`)의 정상 서버 재조회.
- 보강·개정 자료유형 불일치, 기준 원본키 오류, 앵커/삽입 위치 오류, Drive 파일ID 불일치, 페이지 누락, 비활성 페이지 검출.
- 서버 통신 장애 후 재시도 성공 및 모든 대기 배치 파일 보존.
- **업로드→관계검증→토픽 변경** 순서 강제; 관계검증 실패 시 토픽 쓰기 차단 및 다시 저장 시 진행.
- 기존 실제 2페이지 PDF 분할, 원본·서브노트 순차 이동, 개정 첫 장 마지막 발행, 기존 기술용어/가독성 회귀시험 포함.
- CI 완료 결과는 실제 GitHub Actions 성공 여부로 판단할 것; 코드 작성만으로 통과를 선언하지 않음.

## 4. 별도 남은 위험
- 관계 재조회는 운영 `PDF페이지관계` 실제 행을 간접 검증하지만 **`PDF페이지키` 관리표의 자료유형 자동 수정은 수행하지 않음**. -R 키 생성 시 보강으로 기록될 수 있다는 문제는 서버 정책 수정 필요성이 별도 존재.
- 전체 분할 업로드는 원자적 트랜잭션이 아니며, 일부 페이지가 남을 가능성은 유지.
- 서버가 페이지 파일 전체 목록을 반환하므로 다중 보강/개정 저장 시 **읽기 요청 1회와 검증 시간이 추가**됨.
- 실제 모바일 대용량 PDF 분할, 서브노트 신규 파일 업로드, -ADD/-R 실제 운영 파일 저장, 실제 네트워크 중단 후 복구는 미실시.
- PDF 원본 전수 본문 내용 검증이나 기술사 토픽 콘텐츠 전수검수는 별도 작업.
