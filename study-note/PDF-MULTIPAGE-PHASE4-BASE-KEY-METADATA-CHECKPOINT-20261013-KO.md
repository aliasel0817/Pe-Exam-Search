# 학습노트 PDF 안전성 4차 점검 — 기준 원본키 선택 보호 / 개정 페이지키 메타데이터 (2026-10-13)

## 1. 기준선과 발견한 위험
- 기준 운영 main: `4b4acb9d2b5ee0cb9cbf70940306dfaf8b31ee5d`, PWA `4.6.11-all-material-multipage-rc1`.
- 작업 브랜치: `fix/study-note-pdf-base-key-guard-20261013`; Draft PR #13.
- 사용자가 실사용을 확인한 **T4036 교재 신규 원본 2페이지**는 정상 등록 기록으로 보존.
- 보관된 Apps Script `Code.gs`의 `createReferencePdfPageKeyMapping_`는 새 페이지키를 만드는 **첫 업로드의 자료유형**으로 페이지키 등록표를 구성함.
- 프런트의 다중 개정 로직은 미완성 개정의 조기 표시를 막기 위해 `-R숫자` 키의 계속 페이지를 `보강`으로 먼저 업로드하고 **개정 첫 장을 마지막에 등록**함. 따라서 신규 `-R` 키의 관리표 자료유형이 `보강`으로 남을 **가능성**이 있음.
- `PDF페이지관계`는 페이지별로 별도 `개정/보강` 유형을 관리하고 프런트의 `buildReferencePdfLogicalSequence`는 이 페이지별 관계를 사용함. 페이지키 관리표 유형을 보고 다른 문서의 원본으로 재선택하면 사용자가 혼동할 위험이 있음.
- **실제 운영 -R 업로드 후 시트 상태가 확인되지 않았으므로 확정 장애로 기록하지 않음.**

## 2. 구현 변경
- PWA 후보 버전 `4.6.12-pdf-reference-base-key-guard`.
- `isReferencePdfOriginalBaseKey`: 출처유형과 관계없이 페이지수가 1 이상이고 자료유형이 `원본`인 키 중 보강 `-ADD숫자`·개정 `-R숫자` 형태를 제외.
- 새 PDF 자료 등록의 **기준 페이지키 드롭다운**은 교재/서브노트 모두 기존 원본키만 표시.
- 저장되지 않은 과거 선택값이나 잘못 선택된 키는 안전한 기존 원본키로 선택 복구.
- 자료유형이 잘못 기재된 `-R` 키를 직접 선택하더라도 **등록계획 요청 이전에 오류로 중단**, 새 원본/누락/보강/개정 유형 모두 적용.
- 기존 PDF 연속페이지 목록/연결·확대·OCR·원문·학습상태·인증·TTS를 수정하지 않음.

## 3. 자동 테스트
- `study-note/tests/test_reference_pdf_multipage.cjs`에 원본키 `SW`, `SW-2` 유지 / `-ADD1`, `-R2`, **원본으로 잘못 표기된 `-R3`** 제외 / 유효하지 않은 선택복구 시나리오 추가.
- 직접 등록준비에서 잘못 표기된 `-R3` 키를 사용하려 해도 API 등록 계획 자체를 보내지 않는지 검증.
- 기존 2/3페이지 분할, 누락·보강·개정 순차 업로드, 실패 재시도, 서버 재조회 논리순서, 기존 기술용어 가독성 회귀시험은 CI에 유지.

## 4. 한계 및 추가 QA
- 이 변경은 **프런트 기준키 선택 보호**만 제공. 서버 `PDF페이지키` 시트의 기존/향후 자료유형 값을 직접 바꾸지 않음.
- Apps Script 배포 중인 실제 코드의 최신 내용·버전과 보관 `Code.gs`의 완전 일치 여부는 미확인.
- 최초 개정 PDF 실제 등록 이후 `PDF페이지키`와 `PDF페이지관계`의 자료유형과 개정 연속 페이지 조회 순서를 교차 검증해야 함.
- 신규 서브노트 및 보강·누락·교체 실제 쓰기 실험은 신뢰기기에서 사용자 승인된 비충돌 자료로만 수행.
