## 1. Stage 2 목표
기존 일반 학습기록·학습계획·PDF/첨부/주석 및 신뢰기기 인증을 유지하면서, PC·태블릿·모바일에서 **동일 학습계획, 신규 토픽 편입 결과 및 계획 ID+날짜+토픽 ID 단위 회독 완료/다시보기**를 안전하게 동기화하는 **서버·클라이언트·초기 병합의 확정 설계서**를 작성한다.

## 2. 수행 요구
1. GitHub 최신 `main`, 운영 Pages, 실제 배포 Apps Script와 미병합 PR 재확인. 다른 채팅/장비/브랜치 작업과 충돌 여부 확인.
2. 데이터 모델 초안 및 대안 비교: (가) `학습계획` 헤더, (나) `학습계획일정` 일자별 ID/그룹, (다) `학습계획진도` 희소 기록. 100일×3800개 계획은 대용량이므로 단일 Sheets 셀 직렬화 금지. 실제 시트 구조는 **아직 생성하지 않는다**.
3. 데이터 키: `planId`, `date`, `topicId`, `status(todo/done/miss)`, `revision`, `updatedAt`, `deviceId`, `operationId`. 서버 소유 단조 증가 버전과 상태변경 규칙, 삭제/취소(tombstone) 정책, 일정/진도의 참조 무결성 결정.
4. 서명된 조회·쓰기 API 명세: `studyPlans`, `studyProgress`, `saveStudyPlans`, `saveStudyProgress` 등의 action 명칭은 설계 시 확정. 인증은 기존 ACTIVE·HMAC·nonce·requestId/pollKey 재사용. 읽기/쓰기 권한, 검증, LockService, 충돌 코드, 재전송 멱등성, partial failure, 안전한 배치 크기를 명시.
5. **최초 동기화 상세 순서**: 각 기기의 계획·진도 백업 → 서버 읽기 → 서로 다른 기본 plan 버전(신규 24 토픽 여부 등) 비교 → 병합 미리보기/충돌 표시 → 사용자 승인 → 업로드 → 다운로드 → 최종 비교. 읽기 전 새 시드로 덮어쓰는 동작 금지.
6. 이미 존재하는 각 기기 기록은 재작성·삭제 금지. 같은 `planId`인데 일정이 서로 달라질 경우 무조건 한쪽을 최신으로 채택하지 말고 명시적 병합/충돌 보류 규칙 제시. 진도 `done` vs `miss` 동시 변경 충돌도 사용자 데이터 보존.
7. 오프라인 queue, 재시도, 네트워크 타임아웃 후 조회·중복 전송 제어, 초기에 사용한 정적 기본 계획과 새 기기 가입 후 가져오기, 클라이언트 시계 차이 대응 설계.
8. 기존 `학습정보 동기화` 버튼을 이용해 일반 학습정보+학습계획+진도를 통합하는 UX, 현재 상태·최종 성공 시각·미전송 건수 표시, 기존 `학습계획 추가·진도 백업/복원 사용 안내` 문구 수정 위치를 계획한다. 원래 수동 JSON 백업·복원 기능 유지. 현재 UI에 남은 구형 안내 번호 **②/③**와 실제 섹션 **④/⑤**의 불일치도 전수 점검·수정 계획에 포함한다.
9. 배포 순서: 격리된 Google Sheets 사본/테스트 Apps Script → 프런트엔드 독립 브랜치 → 제한적 프리뷰 → 수동/자동 승인 → 실제 원장 보존 확인 → 운영 반영. 배포/롤백 기능 토글의 안전한 기본값과 불변식 설계.
10. 사용자 요구 비중 80:20: 추측성 광범위 QA 확장 대신 필수 충돌·오프라인·기존 진도 보존·인증/회귀 경량 검사에 집중. Stage 2에서는 **실행 검사보다 명세의 결정 가능성**을 중심으로 결과 제출.

## 3. 반드시 산출할 설계 문서

- `STAGE2-CONFLICT-MIGRATION.md`: 최초 동기화 충돌표, 중복/타임아웃/오프라인/롤백 정책
