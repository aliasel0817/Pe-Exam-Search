## 3. 자료 유형별 페이지키 / 연결 / 표시 규칙

| 자료 유형 | 분할 페이지키 / 페이지번호 | 토픽 직접 연결 | 뷰어 표시 방식 |
|---|---|---|---|
| 새 원본/새 문서 | 새 원본 키 `SW-4:1, SW-4:2, ...` (예시) | 새 키 첫 장만 | 해당 새 원본 내부에서 다음/이전 이동 |
| 보강 | 별도 `SW-2-ADD#` 키의 `:1, :2, ...` | 보강 첫 장만 | 지정한 원본 페이지 앞 또는 뒤에 전체 보강 문서 연속 배치 |
| 개정 | 새 `SW-2-R#` 키의 `:기준번호, :기준번호+1, ...` | 개정 첫 장만 | 첫 장은 기준 원본의 활성 개정본, 남은 장은 그 뒤에 연속 표시 |
| 기존 원본의 누락 | 기존 키에 지정한 실제 시작번호부터 연속 등록 (`SW-2:613, SW-2:614`) | 시작 장만 | 기존 원본 번호 순서로 이동, 중복 발견 시 거부 |
| 기존 **원본 페이지**에서 2페이지 이상 파일 교체 | 새 `-R#` 버전 키 발급: 개정 첫 장 + 추가 장 | **기존 원본 토픽 연결 유지** | 기존 원본을 열면 새 개정본 1장부터 보여주고 다음 장으로 이동 |
| 기존 페이지 직접 **1페이지** 파일 교체 | 기존 페이지키 유지 | 기존 연결 유지 | 기존 `replaceReferencePdfPage` 동작 유지 |

### 개정 연속 페이지 데이터 표현
현재 Apps Script `uploadReferencePdfPage`는 개정 페이지에 단일 대체대상 페이지토큰을 요구함. 추가 개정 페이지는 같은 **새 -R# 페이지키**에 속하되, 기준 원본의 **뒤에 배치되는 보강 관계 메타데이터**로 업로드함. 프런트 뷰어는 `-R#`와 기준 원본을 확인해 **활성 개정본에 속한 추가 페이지**를 첫 장 바로 다음에 연결함. 예전 개정 버전의 연속 페이지는 최신 화면에 섞지 않으며 Drive 원본은 보존.

### 교체 범위의 명시적 경계
기존 파일 목록에서 다중 PDF를 선택해 교체할 때 **선택한 원본 한 페이지의 개정본**을 등록하는 것이며, 뒤따르는 **다른 기존 원본 페이지를 삭제·덮어쓰기하지 않음**. 기존 **여러 페이지 범위 전체를 교체**하는 별도 기능은 현재 구현 범위가 아니며, 원본 데이터 보호를 위해 자동 판단하지 않음. 보강·개정 페이지 자체의 목록에서 직접 다중 교체하려면 새 보강/개정 등록 메뉴를 사용하도록 안내함.

## 4. 구현·안전
- 메인 HTML: `study-note/study-note.html`만 기능 수정. Apps Script / SW / manifest 미수정.
- 새 원본·보강·개정·누락 등록 폼과, 직접 누락 PDF 선택 행 및 기존 원본 페이지 교체 선택 행의 다중 파일 처리 확장.
- 프런트 PDF-Lib을 사용한 개별 1페이지 분할; 기존 백엔드 API 1페이지 전송 규약 유지.
- PDF 입력 64MB 이하, 최대 200페이지, 개별 분할본 8MB 이하. 새 키·페이지번호·기존 페이지 중복 방지.
- 같은 자료종류에서 여러 미저장 다중 문서가 동시에 생성되지 않도록 중복 준비 차단.
- 개정 페이지키가 기존에 쓰였을 경우 별도의 사용하지 않은 `-R#`를 선택해 계획 재요청.
- 네트워크 중단 후 같은 관리창에서 미업로드 페이지 재시도 가능. 이미 업로드된 파일은 자동 삭제/덮어쓰기하지 않음.
- **각 페이지는 별도 API 트랜잭션**이라 전체 배치 원자성은 없음. 중간 저장 실패 시 부분 파일이 남을 수 있음. 후속 개선 시 배치 작업 로그/복구 지원 검토.
- 기존 1페이지 교체 API는 이전 동작을 보호하기 위해 유지.
