# 학습노트 다중 기기 학습계획 동기화 — 5단계 전체 작업요청서

## 1. 목표

4단계에서 개발한 안전한 로컬 outbox·동기화 클라이언트를 기반으로 **기기별 기존 학습계획·진도 데이터를 잃지 않는 최초 동기화/통합 마법사**를 별도 feature 브랜치에 구현하고 합성 서버·독립 브라우저에서 검증한다.

**주의:** Stage 3 격리 Apps Script 실배포/HMAC/실제 Sheets 처리 검증은 미완료. Stage 5에서도 운영 API 연결, LIVE 원장 쓰기, 사용자 실제 기기 데이터 자동 통합·main 배포 금지. 실제 운영의 최초 통합은 Stage 8 배포·사용자 명시적 승인 이후에만 실행할 수 있다.

전체 프로젝트 작업 비중: **개발·설계 80%, 표적 검수·출시 20%**. 최종 승인 없이 Stage 6을 진행하지 않는다.

## 3. 수행 작업 (4개 영역)

### 3-1. 기기별 모든 기록의 원본 스냅샷·백업 및 검증

1. 각 브라우저/기기를 최초 통합 전 독립적 대상으로 본다. **현재 사용자의 PC/태블릿/모바일 데이터를 자동 열람하거나 수정하지 않는다.** 자체 소유 합성 프로필로 테스트한다.
2. \`plans\` **모든 planId**와 \`progress\` **모든 기록** 및 동기화 보조 \`pendingOps\`/\`syncConflicts\` 내용을 읽기 전용으로 확보. 기존 '선택 계획 JSON 백업'은 전체 계획 백업이 아니므로 신규 **전체 계획+진도 일괄 JSON 백업** 기능이 필요.
3. 각 백업에 생성 시각, 장치별 임시 식별자, 계획 개수/일정 수/진도 수, canonical SHA-256 manifest, 포맷 버전 및 파일 무결성 검증을 포함. 비밀 세션·Google OAuth 토큰·보안 키는 절대 내보내지 않는다.
4. 사용자가 백업 파일을 실제로 저장하고 무결성 검증을 마치기 전에는 원격 데이터 적용/로컬 덮어쓰기를 하지 않는다. 실패·취소 시 기존 로컬을 그대로 사용할 수 있어야 한다.
5. \`preSyncSnapshots\`에 검증된 마이그레이션 스냅샷과 상태를 기록하되 기존 \`plans/progress\`를 삭제·clear하지 않는다. 12MB 기존 파일 한계와 용량 초과/브라우저 저장공간 한계는 별도 오류·분할 백업으로 처리.

### 3-2. 로컬/서버 계획·진도 비교 및 3-way 병합 미리보기

1. 정적 기본 계획, 현재 로컬 계획, 원격 활성 계획 3가지 기준의 ID/날짜/회독/토픽/그룹/순서/hash를 비교한다.
2. 동일 planId·동일 hash는 한 계획으로 인식하되 그에 연결된 다른 기기의 진행 기록은 합친다.
3. 변경이 안전하게 추가된 슬롯만인지, 같은 토픽의 회독별 날짜가 달라진 것인지, 기존 일정이 삭제/변경된 것인지 **유형을 분류**한다. 원본 일정은 임의 삭제하거나 통째로 덮어쓰지 않는다.
4. 과거 N/비활성 토픽의 기존 계획/진도는 보존하고, 신규 배정 대상은 현재 Y 규칙을 적용한다.
5. 진도 \`planId|date|topicId\`의 \`done/miss/todo\`를 **날짜별 독립 처리**. done vs miss 상충 시 양쪽 원본·출처를 보류함에 보존하고 자동 최신 우선 덮어쓰기 금지.
6. 로컬에만 있는 계획, 서버에만 있는 계획, 같은 이름 다른 planId, 서로 다른 신규 24토픽 편입 일정을 구분하고 **승인 전 병합 결과/삭제 없음/추가 수량/충돌 수량**을 사용자에게 표시.
7. 원격 모든 계획·진도 읽기는 서명된 시험 전용 API를 이용하며, 다운로드 청크·highWatermark·hash 검증에 성공한 후에만 미리보기 상태로 진입한다.

### 3-3. 사용자 확인 후 단계적 통합·재개·복구 기능(합성 환경)

1. 단계: \`UNINITIALIZED→BACKED_UP→COMPARED→REVIEW_REQUIRED→UPLOADING→VERIFIED→SYNC_READY\`. 오류/취소/충돌/재시도는 별도 상태로 표시.
2. **첫 통합 승인**: 확인 후 서버에 없는 독립 계획/진도만 업로드하고, 충돌 항목은 별도 보류. 충돌 없는 원격 변경만 로컬에 반영한다.
3. 서버 \`activeRevision\`/계획 hash/진도 event seq 검증 후 현재 기기만 \`migration.state='ready'\` 설정한다. 백업과 서버 상태 불일치 시 ready 금지.
4. 여러 기기 최초 실행은 각 기기에서 다시 확인·백업·병합해야 한다. PC를 먼저 통합했다고 해서 태블릿/모바일 원본을 자동 폐기하지 않는다.
5. 중간 실패/오프라인/ACK 유실 시 동일 영속 operationId로 재개하고 이미 완료한 부분을 중복 추가하지 않는다. 서버 기록 복구도 기존 revision을 물리 삭제하지 않는다.
6. 백업 복원은 사용자 명시적 확인 후 로컬 **새 상태**를 복원하되 기존 데이터·서버를 무조건 덮어쓰지 않는다. '기기 간 동기화'와 'JSON 백업/복원'은 UI에서 구분한다.
7. Stage 4의 일관성 문제(다중 pending에 따른 CAS/동기화 커서, 새 계획 revision, UI 불일치)를 발견하면 동일 신규 브랜치/PR에서 근거와 테스트를 포함해 보완한다.

### 3-4. 최소 핵심 검수·단계 인계

- v1 DB에서 이미 학습한 기록을 그대로 읽고 전체 JSON 백업→검증→복원한 결과에 변화/손실이 없음을 확인.
- 서로 다른 기기에서 같은 계획 ID/다른 신규 토픽 편입일과 서로 다른 진도가 있는 합성 입력을 병합 미리보기, 충돌 보류, 부분 수렴으로 확인.
- 기존 완료 vs 다시보기 충돌의 자동 덮어쓰기 0건, 기존 3812 토픽/19060회 일정 불변성, 오프라인 재시도.
- 최초 통합 도중 종료/취소/오프라인/서버 미지원/인증 실패 시 원본 보존, 다음 진입에서 복구·재개.
- 기존 학습계획 생성/편입/필터/페이지 이동 및 일반 학습정보, PDF·첨부·필기 핵심 회귀가 정상인지 합성 브라우저에서 확인. 사용자 소유 PC/태블릿/모바일 검수 결과와 자동 검사는 별도 분류.

## 4. 작업 안전 원칙

- 운영 Google Sheets LIVE MASTER의 원문·학습정보·기기관리·PDF/첨부/필기 데이터 **수정·삭제·재배열 절대 금지**.
- 사용자 기기별 \`plans/progress\` 실제 데이터를 사용자 승인 없이 접근·초기화·덮어쓰기·동기화 금지.
- 운영 Apps Script/Script Properties/배포 및 GitHub \`main\`/Pages 변경 금지. Stage 5는 격리 시험 소스와 합성 데이터만 사용.
- 다른 채팅이 이용하는 원격 Windows PC·Git 저장소·PID·서버는 소유권 없는 조작 금지.
- 별도 브랜치/Draft PR 사용; 최신 main/미병합 PR·실제 운영 소스 충돌 확인.
- 3단계 실제 Apps Script/HMAC 실서버 검증 누락은 후속 출시 블로커로 기록. Node mock PASS를 실제 Apps Script PASS로 보고 금지.
- 모든 실제 운영 배포는 Stage 8 사용자의 별도 명시적 승인 이후.

## 5. 완료 후 필수 산출물

1. 전체 기기별 데이터 백업·무결성 검증·원본 보존 기능 코드
2. 로컬/서버 3-way 일정 비교·진도 충돌 보류 및 사용자 승인 UI
3. 합성 PC/태블릿/모바일 통합·재개·복구 결과와 제한 사항
4. Draft PR/기준 commit/변경 파일 목록 및 이전 Stage 1~4 결과 보존 증거
5. 실제 운영 서버/기기 테스트 미실시 여부, 미완료 위험·차단 조건
6. **6단계 UI·사용 안내 개선을 위한 전체 작업요청 메시지를 채팅 본문에 전문으로 제공**(링크만 제공 금지).

## 6. 종료 규칙

기존 데이터 보호 + 합성 환경 최초 통합 검증까지 수행. 운영 main 병합/운영 Script 배포/실사용 기기 데이터 통합은 Stage 8 승인·출시 이전에 수행하지 않는다. 작업 후 결과를 먼저 보고하고 6단계 개발은 별도 사용자 요청으로 진행한다.
